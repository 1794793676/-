# 高校学工平台软件实现与团队协作对接

本文件供实验三四名成员在各自工作环境中继续开发、记录站会和完成 Git 协作。依据为用户最新提供的实验二修订版成员表、实验一的需求分解与验收标准、实验二的 Sprint 目标与 Task 清单，以及本仓库代码。岗位分工说明工作归属；每位成员应核对 AI 生成的改动、亲自运行验证，并以实际操作留下提交和评审记录。

## 一、基线与范围

| 来源 | 已确定内容 | 对本次实现的约束 |
| --- | --- | --- |
| 实验一 | V1 主链为 US01 通知、US02 申请、US03 辅导员初审、US04 学院复核、US05 学生处公示、US06 进度及最终结果；US07 补正属 V2，US08 统计属 V3 | 公示是“拟入选”，最终确认须另有学生处动作；驳回须有理由，权限与脱敏在服务端执行 |
| 实验二 | Sprint 1 选择 US01–US03、21 个 Task、104 理想小时；原计划两周不等于实际已工作两周 | 可运行增量止于“待学院复核”或“已驳回”，不能称已经完成 US04–US06 |
| 实验三 | 站会三问、看板、GitHub Flow、Conventional Commits、冲突处理、配置项、至少两次变更申请、评审、标签与 Release Notes | 只记录真实动作、时间与证据；未经其他成员评审不合入 `main` |

起点：`main` 目前是项目骨架。实验二代码及实验三初稿在 `feature/config-management-docs`，对应草稿 PR #1。先由至少一名其他成员审查 PR #1、复测并处理意见；合并后各人从更新的 `main` 新建自己的分支。仓库当前公开，上传真实学籍、联系方式、申请附件或凭据前须先处理可见性和脱敏。

## 二、现有软件如何运行

运行环境为 Python 3.10 及以上，业务服务和测试只用标准库。`scholarship/domain.py` 管业务规则与 SQLite，`scholarship/server.py` 管本机 HTTP 路由、会话和 CSRF；`scholarship/static/` 是中文 HTML/CSS/JavaScript 界面；`tests/` 是单元、路由和真实 HTTP 集成测试；`scripts/po_acceptance.py` 是验收复现脚本。`examples/` 的两个 PDF 是教学样例。

在仓库根目录执行：

```sh
python -m scholarship.server --port 8080 --data-dir runtime
python -m unittest discover -v
```

浏览器访问 `http://127.0.0.1:8080`。演示账号为 `student1`、`student2`、`student3`、`counselor1`、`counselor2`，演示密码均为 `demo123`。`runtime/` 是本地 SQLite 与附件数据，不入 Git；测试应使用隔离目录。以上账号和数据仅供教学，不是校级 SSO 或真实学生资料。

| 当前接口 | 用途与边界 |
| --- | --- |
| `POST /api/login`、`GET /api/session`、`POST /api/logout` | 建立和清理服务端会话；变更请求需要 CSRF token |
| `GET /api/projects`、`GET /api/projects/{id}` | 已发布通知及其申请时间；未发布通知不返回 |
| `POST /api/uploads`、`GET /api/attachments/{id}` | 上传实际材料、按属主或辅导员范围下载 |
| `GET/POST /api/applications`、`GET /api/applications/{id}` | 本人或负责范围内的申请列表、提交和详情；同学生、项目、批次仅一条申请 |
| `POST /api/applications/{id}/review`、`GET /api/applications/{id}/audit` | 辅导员通过或驳回并保留审核记录；通过后进入“待学院复核” |

现有 SQLite 表为 `users`、`projects`、`applications`、`attachments`、`reviews`。服务端使用登录会话识别操作者，不接受浏览器自行声明角色。申请开放区间是 `[open_at, deadline)`；截止瞬间不可新提交。驳回、重复提交、并发审核和跨用户访问已有测试。引入新状态或表时，应写可重复执行的数据迁移与相应测试，保留旧教学数据可读性。

## 三、后续功能对接顺序

实验三重点是协作与配置管理，不自动扩大 Sprint 1 功能范围。若 PO 将实验一规划的 V1 后半段纳入当前迭代，应先建立变更申请、评估容量和审批，再按下列依赖逐项实施：

1. **US04 学院复核，Dev 1 主责。** 扩展学院审核员身份和学院范围，仅允许处理“待学院复核”的本学院申请；通过转“待公示”，驳回转“已驳回”且理由非空。审核人、时间、意见进审计记录。先补单元与 HTTP 测试，再改服务端，最后接界面。
2. **US05 学生处公示，Dev 2 主责。** 只从本项目批次的“待公示”记录整批发布；时间范围必须有效，部分记录不合条件则整批不变。公开名单使用明确字段白名单：脱敏姓名、脱敏学号、学院、项目、拟获等级；不得输出联系电话、附件或家庭经济详情。公示状态为“公示中”，不是最终获批。
3. **US06 进度与最终结果，Dev 2 主责，PO 验收。** 申请人只能看本人进度和结果。公示期结束且学生处确认线下异议已处理后，才允许对整批记录形成“已获批”或“未获批”终态；未获批要有原因，确认人和时间留痕，禁止部分提交。公示结束本身不自动获批。

顺序为 US03 → US04 → US05 → US06。US07、US08 不在这一轮默认范围。每个新增 API 的请求字段、响应字段、错误码、数据迁移和界面动作由开发者在 PR 描述中列清，PO 按实验一 Given/When/Then 验收；没有审批的功能不合入基线。

## 四、成员任务与各自 AI 工作提示

四人的姓名与岗位以最新实验二修订版为准。下面的提示可分别发给各自的 AI；每人应自己检查结果并执行提交。提交作者用本人 Git 身份仅适用于本人实际负责并确认的改动。

### 陈铎锋：PO

负责范围、优先级、验收和变更审批。核对实验一 US01–US08 与实验二 Sprint 1，明确本次是否纳入 US04–US06；建立至少两张真实变更申请 Issue，写明理由、范围、工作量与风险，请 SM 和开发者评估后给出是否纳入本轮的决定。按验收标准实际运行正常、异常、越权路径，记录版本、命令、结果和阻断问题；不替开发者提交实现代码。可提交 `docs/product/` 下的范围、验收矩阵和审批记录，提交信息示例为 `docs: 确认本轮故事范围与验收标准`。

给 AI 的提示：**“我是 PO 陈铎锋。请基于实验一 US01–US08、实验二 Sprint 1 和当前仓库，先列出本轮与后续范围，再帮我起草两张可审查的变更申请及 US01–US03 验收矩阵。不要替我写审批结论或验收通过；我会按实际执行结果补齐。改动放在独立 `feature/po-scope-acceptance` 分支，展示 diff 和验证步骤后由我提交。”**

### 何昊锵：SM 与配置管理员候选

负责组织实际站会，按三问记录各人的真实汇报、障碍和看板状态；核查 5 分钟时间盒及障碍跟踪。维护配置项清单、分支/提交约定、PR 评审与变更流程；协调至少一次 README 同行冲突演练，并保存冲突出现、人工消解与合并的证据。协助团队核对 PR #1；在功能和测试满足发布条件后准备 Release Notes，由团队确认版本号，再打注释标签和发布。可提交 `docs/scm/`、站会记录与发布草稿，示例为 `docs: 记录站会障碍与配置项基线`。

给 AI 的提示：**“我是 SM 何昊锵。请核对实验三步骤 1–10 与当前 GitHub 仓库，建立可填写的站会、看板、配置项和冲突演练记录，并检查 PR #1 的提交范围。只能录入我提供的真实参会、评审、时间和测试证据；未发生的事项保留待办。改动放在 `feature/sm-scm-records`，给我逐项核对后再提交。”**

### 陈志成：Dev 1

负责申请、辅导员审核、状态流转与验收标准。先复测现有 US01–US03 的 `domain.py`、`server.py`、对应单元及 HTTP 测试，审查 PR #1 相关代码。如 PO 批准 US04，则在 `feature/college-review` 上先写失败测试，再完成学院角色、范围校验、复核状态及审计，并补真实 HTTP 链路。与 Dev 2 协作 README 冲突演练时，只提交自己实际修改的分支；不可把测试失败或未合并状态说成已交付。示例提交：`test: 覆盖学院复核权限与状态`、`feat: 实现学院复核`。

给 AI 的提示：**“我是 Dev 1 陈志成。请先复测并评审现有 US01–US03，不改无关模块。若提供了 PO 批准的 US04 变更申请，再按实验一验收标准实现学院复核：先测试后代码，覆盖跨学院、非法状态、空驳回理由、重复审核和审计原子性。每个独立功能点单独提交到 `feature/college-review`，提交前向我展示 diff 与测试结果。”**

### 涂先诚：Dev 2

负责公示、结果、权限隐私与验收复核。先审查当前服务端权限和附件访问边界，以及 PR #1 的相关测试；可对发现的真实缺陷开 `bugfix/*` 分支。若 PO 批准 US05、US06 且 US04 已有可测试接口，再在 `feature/publication-results` 上实现整批公示、字段白名单与脱敏、最终确认、本人结果页和对应测试。与 Dev 1 互审 PR，重点检查状态与隐私。示例提交：`test: 覆盖公示脱敏与越权访问`、`feat: 实现拟入选公示`。

给 AI 的提示：**“我是 Dev 2 涂先诚。先审查当前申请和附件的角色边界，列出有证据的问题；不要把 US05/US06 写成已实现。只有拿到 PO 审批及 US04 接口后，才按实验一 GWT 做整批公示和最终结果，先写失败测试，重点覆盖脱敏白名单、非法发布、批次原子性、未结束公示与他人结果访问。改动放在 `feature/publication-results`，由我核对后提交。”**

## 五、协作、验收与发布交接

1. 每人克隆仓库，在自己的克隆中配置 `git config user.name` 与 `git config user.email`；先审查 PR #1，至少一名非提交者评审并复测后才合并。不要强推、改写已有共享历史或直接把功能提交到 `main`。
2. 后续从最新 `main` 建 `feature/*` 或 `bugfix/*`，按独立功能点提交。推送并开 PR，描述关联 Issue、实际修改、测试命令与结果、风险和截图/日志；至少一位其他成员评审。AI 可以辅助写代码，成员应对自己确认的改动负责。
3. 冲突演练由 Dev 1、Dev 2 在两个分支修改 README 同一行，分别提交；第一个经评审合入后，第二个更新 `main`，实际观察冲突标记、人工合并并复测，再经评审合入。SM 保存命令输出和最终提交，不使用 `push --force`。
4. 站会记录采用“昨天完成、今天计划、障碍”三问；SM 会后更新待办、进行中、已完成、阻塞状态。两次变更申请必须分别有提出、评估、PO 审批、实施、评审测试、合入基线的真实证据。
5. 每次 PR 至少运行受影响测试；全量复核命令为 `python -m unittest discover -v`。当前导入分支在允许本机 HTTP 连接的环境运行过 53 项测试且通过；这只证明 US01–US03 现有测试通过，不证明 US04–US06 或实验三流程已完成。
6. 发布前复核代码、配置项、站会/变更记录、PR 评审和全量测试。`v1.0.0` 只在团队确认对应发布范围确实可发布时创建；Release Notes 写实际功能、已知问题和版本提交。实验一规划的 V1 完整 MVP 需要 US01–US06，不能把仅到辅导员初审的增量描述成完整 MVP。

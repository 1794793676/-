## 1. 通用约定（沿用现有，未变更）

统一响应包装，前端现有的 `api()` 封装已按此解析：

```json
{ "ok": true,  "data": { } }
{ "ok": false, "error": { "code": "ALREADY_REVIEWED", "message": "申请已处理，不能重复复核", "details": [], "current_status": "待公示" } }
```

- 登录后从 `POST /api/login` 或 `GET /api/session` 取 `csrf_token`；**所有非 GET/HEAD 请求**带 `X-CSRF-Token`
- `credentials: "same-origin"`、`Content-Type: application/json`
- 仅允许本机 Host（`localhost` / `127.0.0.1`），跨站 Origin 被拒绝
- `session.user.role` 现有取值 `student`、`counselor`，**本轮新增 `college_reviewer`**
- `session.user.college` 是服务端判定数据范围的依据；**角色只能用来决定渲染哪个表单，不能用来判定「能不能看」**——权限以服务端 SQLite 为唯一真相源
- 本轮新增两个演示账号：`college1`（计算机学院）、`college2`（文学院），密码沿用现有统一演示密码（见登录页预填值，或 `scholarship/domain.py` 的 `DEMO_HASH`）

## 2. 变更一：提交过程的时序约定（PR #3，已合并）

### 2.1 修的是什么

原先 `submitApplication` 在多个异步上传与最终申请请求里反复读取全局 `selectedProject`。学生在第一个附件上传 pending 期间点开另一个通知，`openProject()` 会覆盖这个全局变量，导致第二个附件和申请被提交到**另一个项目**，最终因材料不属于该项目而失败。只有提交按钮被禁用，通知导航仍可点。

### 2.2 前端必须遵守的契约

一次「点击提交」视为原子操作：

1. 点击瞬间把当前通知存为**局部快照** `const project = selectedProject`
2. 本次产生的所有 `POST /api/uploads` 与最终 `POST /api/applications`，`project_id` **一律取 `project.id`**
3. 提交进行中（`sending === true`）不得调用 `openProject()` 覆盖全局选中项；界面给出提示「正在提交申请，请等待完成后再切换通知」
4. `finally` 恢复按钮状态时同样使用 `project.can_apply`，不得重新读全局

```
点击提交 → 快照 project ─┬─ POST /api/uploads      project_id = project.id
                        ├─ POST /api/uploads      project_id = project.id
                        └─ POST /api/applications project_id = project.id
                                                 attachment_ids = [上面两个 id]
   ↑ 整个过程中 openProject() 被锁定，selectedProject 不参与本次请求
```

### 2.3 界面动作变化

| 动作 | 修复前 | 修复后 |
| --- | --- | --- |
| 上传期间点击其他通知 | 静默切换项目，导致提交失败 | 拒绝切换并给出提示 |
| 提交按钮恢复状态 | 按后来打开的通知判断 | 按提交开始时的快照项目判断 |
| 请求字段 | 无变化 | 无变化（`project_id` / `fields` / `attachment_ids` 不变） |

> **新增 API：无；请求字段 / 响应字段 / 错误码：无变更。** 前端若有自己的并行上传或重试逻辑，同样以快照为准。

## 3. 变更二：US04 学院复核新增接口（PR #5）

### 3.1 端点

```
POST /api/applications/{id}/college-review
```

与辅导员端点是**两个独立接口**，不要复用 `/review`：

| 端点 | 允许角色 | 处理的状态 | 通过后状态 |
| --- | --- | --- | --- |
| `/api/applications/{id}/review` | `counselor` | `待辅导员审核` | `待学院复核` |
| `/api/applications/{id}/college-review` | `college_reviewer` | `待学院复核` | `待公示` |

### 3.2 请求字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `decision` | string | 是 | `approve` 或 `reject`，其他值返回 `INVALID_DECISION` |
| `opinion` | string | 否 | 复核意见，最长 2000 字符，服务端 `strip()`；`reject` 时**必须非空** |

```json
POST /api/applications/APP-516343315950450E/college-review
X-CSRF-Token: <session.csrf_token>
Content-Type: application/json

{ "decision": "approve", "opinion": "学院复核通过" }
```

### 3.3 成功响应（HTTP 200）

```json
{
  "ok": true,
  "data": {
    "id": "APP-516343315950450E",
    "student_id": "student1",
    "project_id": "open",
    "batch": "2026秋季第一批",
    "fields": { "phone": "13800000000", "application_reason": "学业支持" },
    "status": "待公示",
    "submitted_at": "2026-10-19T08:00:00+00:00",
    "rejection_reason": "",
    "attachments": [
      { "id": "489063cb…", "material_key": "transcript", "filename": "transcript.pdf",
        "size": 34, "sha256": "5b4b5ef2…", "content_type": "application/pdf" }
    ],
    "duplicate": false
  }
}
```

| 字段 | approve | reject |
| --- | --- | --- |
| `status` | `待公示` | `已驳回` |
| `rejection_reason` | `""` | 复核意见原文（非空） |

> **注意**：复核响应与现有 `/review` 响应结构一致，**不含 `student_name`**；`GET /api/applications`（列表）和 `GET /api/applications/{id}`（详情）才带 `student_name`。前端在复核成功后请重新拉取详情渲染，不要直接拿复核响应里的学生姓名。

### 3.4 错误码（全部复用既有码，无需新增前端分支）

| 场景 | HTTP | `code` | 附带 |
| --- | --- | --- | --- |
| 未登录 / 会话过期 | 401 | `AUTH_REQUIRED` | |
| CSRF 缺失或错误 | 403 | `CSRF_REQUIRED` | |
| 学生 / 辅导员调用本端点 | 403 | `FORBIDDEN` | |
| 学院审核员访问**其他学院**的申请（详情 / 审计 / 附件 / 复核） | 403 | `FORBIDDEN` | |
| 申请不存在 | 404 | `NOT_FOUND` | |
| 状态不是 `待学院复核`（含重复复核、已驳回后复核） | 409 | `ALREADY_REVIEWED` | `error.current_status` 返回当前状态 |
| `decision` 非法、缺字段、`opinion` 非字符串或超长 | 400 | `INVALID_DECISION` | |
| `reject` 但理由为空白 | 400 | `REASON_REQUIRED` | |

错误示例：

```json
{
  "ok": false,
  "error": {
    "code": "ALREADY_REVIEWED",
    "message": "申请已处理，不能重复复核",
    "details": [],
    "current_status": "待公示"
  }
}
```

前端现有 `api()` 会把 `message`、`details`、`当前状态：current_status` 拼成提示，无需改动。

### 3.5 数据范围与权限

| 接口 | `college_reviewer` 可见范围 |
| --- | --- |
| `GET /api/applications` | **本学院全部申请**（含历史状态，不只是待复核） |
| `GET /api/applications/{id}` | 仅本学院申请 |
| `GET /api/applications/{id}/audit` | 仅本学院申请；含辅导员初审与学院复核两条记录 |
| `GET /api/attachments/{id}` | 仅本学院申请已提交的材料 |
| `POST /api/applications/{id}/college-review` | 仅本学院、**状态为 `待学院复核`** 的申请 |

跨学院请求一律 403，列表里也不会出现，前端不需要自己过滤。

### 3.6 数据迁移与演示账号

`Store.migrate_college_review()` 在每次构造 `Store` 时执行，幂等：补 `college1` / `college2` 两个账号、建 `application_status` 索引；**无新表、无新列、无 ALTER TABLE**，旧教学数据与附件原字节保持可读。复核的状态更新与 `reviews` 插入在**同一事务**内，审计记录含 `reviewer_id / decision / opinion / reviewed_at`。

## 4. 状态机

```
待辅导员审核 ──(辅导员 approve)──▶ 待学院复核 ──(学院 approve)──▶ 待公示 ──▶ [US05 公示中] ──▶ [US06 已获批 / 未获批]
      │                                  │                                      （已在 US05 / US06 实现）
      └──(辅导员 reject，理由非空)──▶ 已驳回 ◀──(学院 reject，理由非空)──┘
```

- `已驳回` 是终态，理由写入 `rejection_reason`，前端展示「驳回理由：…本轮申请已终止」
- **`待公示` 不是最终获批**，只是「拟入选」，前端文案必须写清，不能显示「已通过 / 已获奖」
- 公示、最终结果由 US05 / US06 实现（本文件编写时尚未接入；现已在 `docs/前端接口对接说明-公示与结果.md` 中补齐并完成界面）

## 9. 一个已知细节

测试时钟固定时，同一申请的两条审计记录 `reviewed_at` 可能相同，`GET /audit` 的排序是 `ORDER BY reviewed_at, id`，此时**两条记录的先后顺序不保证**。前端展示审核记录时请按 `reviewed_at` 分组或按 `reviewer_id` 判断环节，不要假定「数组最后一条就是学院复核」。真实运行时钟带微秒精度，两步人工审核不会同刻。

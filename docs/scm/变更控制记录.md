# 变更控制记录（Sprint 1 · 模拟记录）

> **教学模拟说明**：本表为实验三教学模拟稿，演示两次变更申请完整走通"提出 → 评估 → 审批 → 实施 → 验证 → 合入"六步，**不冒充真实审批记录**。实际提交时由提出人、PO、SM 按真实时间与结论填写。

## 一、流程与角色

| 步骤 | 活动 | 负责人 |
| --- | --- | --- |
| 1. 提出变更 | 提交 Issue/任务卡，说明原因与内容 | 提出人 |
| 2. 评估影响 | 评估范围、工作量、风险 | PO + SM |
| 3. 审批 | PO 审批是否纳入当前迭代 | PO |
| 4. 实施 | 在 `feature/*` 分支实现 | 开发成员 |
| 5. 验证 | Code Review + 测试验证 | 其他成员 |
| 6. 合入基线 | 合并到 `main` 并更新版本号 | SM |

## 二、变更登记

| 编号 | 提出人 | 变更内容 | 影响评估 | 审批 | 实施与验证 | 结果 |
| --- | --- | --- | --- | --- | --- | --- |
| CR-01 | PO | US01 通知详情增加"材料清单"字段 | 影响 T01/T04/T05/T06，约 4h，风险低 | PO 批准纳入 Sprint 1 | 在 `feature/us01-notice` 实施；Code Review + 单测 + PO 验收 | 合入 `main`，纳入 v1.0.0 |
| CR-02 | Dev2 | US02 上传增加 ≤10MB 与文件魔数校验 | 影响 T11/T12/T14，约 6h，风险中（需覆盖伪造扩展名） | PO + SM 批准纳入 Sprint 1 | 在 `feature/us02-apply` 实施；安全评审 + HTTP 集成 | 合入 `main`，纳入 v1.0.0 |

### CR-01 说明

- **提出**：PO 在 US01 验收准备时发现通知详情只列材料名称，学生无法一次看清材料要求，提出在详情中增加"材料清单"字段。
- **评估**：涉及通知详情接口字段、详情页渲染与两条验收用例，约 4h；不改变数据库表结构，风险低。
- **审批**：PO 于当日站会后批准纳入本轮。
- **实施与验证**：在 `feature/us01-notice` 分支实现，提交信息带 `Refs: CR-01`；Dev1 评审详情渲染，Dev2 补充详情字段单测，PO 按验收标准复跑。
- **合入**：随 US01 的 PR 合并入 `main`，版本影响为 MINOR 的功能补充（并入首发 v1.0.0）。

### CR-02 说明

- **提出**：Dev2 在实现上传时发现仅校验扩展名可被重命名为 `.pdf` 的文本文件绕过，提出增加文件大小上限与文件头魔数校验。
- **评估**：涉及上传接口、文件落盘、两条单元测试与一条集成测试，约 6h；风险中，需覆盖伪造扩展名、超限、空文件等异常。
- **审批**：PO 与 SM 共同批准纳入本轮，理由是材料真实性直接影响后续审核。
- **实施与验证**：在 `feature/us02-apply` 分支实现（≤10MB、PDF/PNG/JPG 魔数、失败不落库）；安全评审 + 真实 HTTP 集成验证。
- **合入**：随 US02 的 PR 合并入 `main`，版本影响为 PATCH 级的安全修正（并入首发 v1.0.0）。

## 三、登记规则

1. 每项变更先有 Issue/任务卡，再有代码；顺序不能颠倒。
2. 评估必须写清"改哪些配置项、影响哪些已有行为、如何回滚"。
3. 验证证据包括评审人、执行命令、关键输出与失败用例。
4. 合入后判断版本号影响：缺陷修复 → PATCH；向下兼容功能新增 → MINOR；不兼容变更 → MAJOR。
5. 更新本表单独提交：`git commit -m "docs(scm): 登记 CR-__ 审批与合入"`。
